## 一、 我要做一个什么？（选题背景与系统定位）

### 1. 选题切入点与解决的痛点
“今天吃什么”是日常生活中最高频的决策痛点。市面上现有的“随机大转盘”或传统菜谱软件之所以流于表面，是因为忽略了用户在真实餐饮决策中的四大核心约束：
1. **环境与状态约束（选择过载）**：饮食选择高度依赖实时气温降水（如降温下雨想喝热汤）、月底预算余额及当下疲惫程度，随机抽签缺乏上下文感知。
2. **近期味觉疲劳（缺乏防腻机制）**：传统推荐容易连续推荐同类食物，缺乏符合人类直觉的“味觉冷却与防腻去重”机制。
3. **多人聚餐推诿死锁（群组偏好冲突）**：室友拼单或朋友聚餐时常陷入“随便、都行”的社交死锁，缺乏低门槛的实时表决工具与折中共识算法。
4. **外食与下厨割裂（缺乏清库存与搭配逻辑）**：工作日吃食堂/点外卖关注“距离与预算凑单”，周末自己做饭则受限于“冰箱还剩什么临期食材”与“现有厨具（如仅有电饭煲）”。

### 2. 系统定位与“5 + 2”功能架构
本课题并非简单的菜谱增删改查（CRUD）或大模型对话框套壳，而是设计一套**“统一八维风味特征内核 + 外食/下厨双模式无缝切换”**的智能饮食决策系统，涵盖 **移动端用户前台（5大模块）** 与 **PC端管理及实验后台（2大模块）**：

| 所属端 | 核心功能模块 | 具体包含的业务子功能 |
| :--- | :--- | :--- |
| **移动端前台**<br>*(H5 / Android APK)* | **1. 用户主页与饮食基因** | 饮食偏好冷启动问卷、绝对忌口/过敏原红线管理、**美食红黑榜**（收藏提权与黑名单永久过滤）、干饭成就统计、**答辩演示角色一键切换器** |
| | **2. 上下文感知单人决策** | 顶部实时天气环境胶囊、情绪/状态气泡点选、**外食/下厨双模式切换**、**可解释性五维匹配度雷达图**与推荐理由归因 |
| | **3. 虚拟冰箱与下厨规划** | 冰箱现有食材与保质期倒计时管理、基于临期余料与厨具限制逆向匹配菜谱、多菜谱**智能合并同类项生成买菜清单** |
| | **4. 多人“干饭房间”协同** | 扫码免安装进房、WebSocket 实时状态同步、**15秒探探式左滑右滑闪电表决**（含一票否决卡）、群组共识揭晓与各方妥协度分析 |
| | **5. 饮食足迹与防腻账本** | “就吃这个”一键打卡（实时触发防腻算法降权）、近期菜品**味觉冷却进度看板**、周度餐饮消费与口味分布报告 |
| **PC端管理后台**<br>*(Web Admin)* | **6. 多源数据与AI打标台** | 周边真实门店（高德POI同步）与校园食堂档口 CRUD、开源菜谱库管理、**调用大模型 API 批量蒸馏菜品 8 维特征控制台** |
| | **7. 算法沙盒与实验大屏** | 全站饮食数据可视化看板、**算法超参数实时调节沙盒**、**多智能体仿真实验对比图表生成器**（直接支撑论文第五章实验分析） |

## 二、 我准备怎么做？（核心算法与数据工程方案）

为保证毕业设计的学术深度与工程饱满度，本系统采用**“大模型（LLM）离线特征工程 + 白盒数学模型实时计算”**的技术路线，并构建**万级规模**的多源数据集。

### 1. 四大核心算法模型（白盒可解释，非随机抽签）
底层将所有“外食餐馆菜品”和“家常菜谱”统一映射为 **8 维标准化风味特征向量**（辣度、油腻度、汤水感、适宜温度、饱腹度、出餐速度、社交属性、抚慰指数，取值 $0.0 \sim 1.0$），在此基础上实现四个核心算法：

1. **基于艾宾浩斯遗忘曲线的“跨场景防腻时间衰减模型”**：
   根据用户近期打卡流水，计算候选菜品 $i$ 距离上次吃同款菜品的天数 $\Delta t_{\text{exact}}$ 及同菜系/同主料的天数 $\Delta t_{\text{similar}}$，赋予动态衰减权重：
   $$W_{\text{decay}}(i) = \left(1 - e^{-\lambda \cdot \Delta t_{\text{exact}}}\right) \times \left(1 - 0.4 \cdot e^{-\lambda \cdot \Delta t_{\text{similar}}}\right)$$
   实现“中午在食堂吃了红烧牛肉面，晚上回家做饭自动对牛肉与面食降权”的跨场景防腻记忆。
2. **多维上下文感知的单人效用推荐算法**：
   先通过硬过滤剔除命中用户“绝对忌口”与“黑名单”的候选项，再从**口味余弦相似度 $U_{\text{taste}}$、实时天气契合度 $U_{\text{weather}}$、预算友好度 $U_{\text{budget}}$、防腻新鲜度 $U_{\text{fresh}}$、状态/冰箱临期余料匹配度 $U_{\text{status}}$** 五个维度计算归一化得分（直接生成前端五维雷达图），结合红榜收藏提权因子 $\text{Boost}_{\text{fav}}$ 输出总分：
   $$S(i) = W_{\text{decay}}(i) \times \left( \alpha U_{\text{taste}} + \beta U_{\text{weather}} + \gamma U_{\text{budget}} + \delta U_{\text{status}} \right) \times \text{Boost}_{\text{fav}}(i)$$
3. **融合“最小痛苦策略（Least Misery）”的多人协同博弈算法**：
   针对多人房间场景，将每位成员 $u$ 的静态口味先验分（占 $40\%$）与 15 秒实时划卡表决分（占 $60\%$）融合为个体满意度 $R_{u,i}$。在剔除一票否决项（$\text{Mask}_{\text{veto}}$）后，结合**平均满意度最大化**与**最小痛苦策略**计算群组共识分 $G(i)$：
   $$G(i) = \text{Mask}_{\text{veto}}(i) \times \left[ \omega \cdot \frac{1}{M}\sum_{u=1}^{M} R_{u,i} + (1 - \omega) \cdot \min_{u \in M}(R_{u,i}) \right]$$
   既照顾大多数人的喜好，又确保团队中最挑剔的成员不会踩雷。
4. **一餐多菜品组合优化算法（改进背包问题）**：
   在预算上限与荤素冷热互补约束（平均油腻度 $\le 0.65$）下，自动组合“一荤一素一汤”套餐；下厨模式下最大化消耗冰箱临期食材，并自动求差集生成合并同类项的《待采购买菜清单》。

### 2. 万级多源数据工程与仿真验证方案（解决毕设数据量与实验验证问题）
* **第一层：真实门店 + 开源菜谱底座（共约 8,000 $\sim$ 9,700+ 条）**
  * 调用**高德地图开放平台 POI 接口**，抓取高校周边 3 公里内真实餐饮门店（约 1,500+ 家真实店名、GCJ-02 经纬度、人均消费与评分）及 200 个校园食堂窗口。
  * 导入并清洗**开源中式家常菜谱数据集**（约 6,300 $\sim$ 8,000 道菜谱，含主辅料、步骤与耗时）。
* **第二层：大模型批量特征蒸馏（60,000+ 个细粒度标签）**
  * 编写 Python 批处理脚本调用国产大语言模型 API，为全部菜品自动评估并入库 8 维风味特征向量与过敏原标签。
* **第三层：多智能体仿真实验（支撑论文第五章实验对比）**
  * 构建 200 个不同地域口味与预算特征的虚拟大学生画像，通过脚本模拟连续 60 天的饮食打卡流水（24,000+ 条）与 1,000 场四人寝室拼单投票（40,000+ 条），对比测试本系统算法与传统随机/均值推荐在**“连续 14 天菜系重样率”**与**“群组最低满意度（Least Misery Score）”**上的提升效果。

## 三、 我使用什么技术做？（技术栈选型）

系统采用前后端分离架构，技术选型兼顾主流规范与答辩演示的便捷性：

| 架构层级 | 选用技术与框架 | 选型理由与在项目中的作用 |
| :--- | :--- | :--- |
| **后端与算法服务** | **Python 3.10 + FastAPI** | 轻量高效，原生支持 **WebSocket**（实现多人房间实时同步进房与划卡投票），且方便直接用 Python 编写矩阵运算与推荐算法。 |
| **数据库层** | **SQLite / MySQL + SQLAlchemy** | 共设计 **9 张核心关联表**（用户表、饮食基因与红黑榜表、周边门店表、菜品菜谱主表、冰箱库存表、饮食流水表、多人房间表、投票记录表、算法参数配置表）。 |
| **前端与可视化** | **Vue 3 + Vite + Tailwind CSS + daisyUI** | 响应式组件化开发，配合 **ECharts** 绘制可解释性五维雷达图与后台实验对比大屏，集成 **GSAP / Lottie** 实现流畅的探探式划卡与交互动效。 |
| **外部接口能力** | **高德地图 API + 国产大模型 API + 天气 API** | 获取真实周边餐馆 POI 坐标、实时气温降水数据，以及执行离线菜品 8 维特征蒸馏。 |
| **交付与部署形态** | **响应式 Web (H5) + Android APK + PC 后台** | 通过 Capacitor / HBuilderX 将移动端打包为独立 **Android APK 安装包**；同时保留 H5 网页链接，方便答辩现场多人直接微信扫码进入“干饭房间”互动，免去微信小程序繁琐的域名 ICP 备案周期。 |

## 四、 最终做出来是什么样子？（预期交付成果与演示效果）

项目完成后，将交付一套数据充实、交互完整、可直接现场互动演示的软硬件与文档成果：

1. **三端合一的完整软件系统**：
   * **手机端 App（APK 安装包 + H5 网页）**：包含天气感知胶囊、外食/下厨切换、情绪气泡点选、五维雷达图结果弹窗、虚拟冰箱、多人扫码 15 秒划卡房间、防腻冷却账本及个人中心。
   * **PC 端管理与算法实验后台**：包含万级门店/菜谱数据管理台、大模型自动打标触发器、以及直观渲染仿真实验对比曲线的数据大屏。
   * **充实的数据库文件**：包含 9 张数据表、近万条真实周边餐馆与家常菜谱、以及数万条仿真打卡与投票流水。
2. **答辩现场三大核心演示看点**：
   * **看点 1（算法白盒实时调参）**：移动端右上角设有**“算法沙盒调试抽屉”**，答辩时可当场拖动防腻衰减系数 $\lambda$、群组折中系数 $\omega$ 等滑块，主界面推荐排名与五维雷达图实时重算变化，直观证明算法真实运行。
   * **看点 2（多角色一键秒切）**：在用户主页可一键切换“川渝嗜辣党”、“广东清淡养生党”、“月底吃土党”等预设角色，当场对比不同饮食基因与忌口红线下的差异化推荐结果。
   * **看点 3（现场扫码多人拼单）**：现场创建干饭房间生成二维码，支持多台手机扫码进入同一房间进行 15 秒划卡表决，实时揭晓最优折中方案。
3. **毕业论文支撑材料**：
   * 系统需求分析、9 张表 E-R 图、四大算法数学建模、系统实现截图，以及第五章基于 200 虚拟人仿真数据的**《连续 14 天重样率对比折线图》**与**《群组博弈满意度对比柱状图》**。

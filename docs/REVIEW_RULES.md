版本：1.2｜生效/修订日期：2026-10-28｜开发细则：[BATCH4_PLAN.md](../BATCH4_PLAN.md)｜合并编排：[CONSOLIDATED_REMAINDER_PLAN.md](CONSOLIDATED_REMAINDER_PLAN.md)

**历史准入记录**：PC01/R02 → PC02/R01 → PC03/F12 已按逐项门禁完成并获 PASS。当前剩余工作依用户 2026-10-28 决定，按[合并计划](CONSOLIDATED_REMAINDER_PLAN.md)分为 G1–G5 连续施工，全部完成后统一独立审查；S07 纳入 G1，不预先记 PASS。

## 1. 角色、权限和结论来源

- **用户**：决定功能范围、设计变更、素材/数据来源、外部费用和重大取舍。用户的明确新指令优先，变更须记录，不以本规则阻碍用户授权。
- **开发方**：按当前开放大组连续实现组内步骤，提交代码、测试和证据；可以自测，但不得给自己的步骤签发正式 PASS。
- **审查方 Codex（本会话中的审查角色）**：独立读取源码、运行验证、检查实际页面和数据，签发 PASS / FAIL / BLOCKED，维护阶段台账。审查方直接修了问题，也须重新验证，不能因自己写了代码就跳过门禁。

**正式验收依据**：Codex 在统一审查报告中逐项给出子步骤结论、受审源码/数据版本、证据和遗留风险，并更新[阶段台账](review/STAGE_STATUS.md)。最终统一审查前，组内自测、旧截图和用户“基本没问题”的反馈都只能作为线索，不构成正式 PASS。

这是团队协作门禁，不是已经安装的 Git/CI 强制保护。当前没有声称存在自动拦截越步的程序；开发方必须遵守台账，审查方发现越步时拒绝验收、保留用户已有成果，不擅自清空文件。后续若建立 CI，只负责自动检查，不能代替 Codex 的独立审查许可。

## 2. 依据与冲突处理

1. 用户在当前会话中的明确决策与项目 `AGENTS.md`。
2. `MASTER_SPEC.md` 当前有效版本：系统设计 SSOT；附属视觉文件负责其明确引用的视觉细则。
3. `BATCH4_PLAN.md`：施工步骤与各步验收面；本规则：审查方法；阶段台账：执行状态。三者不创设第二套设计 SSOT。
4. `docs/AGENT_MEMORY.md`：工程线索，不是通过凭证；旧审查报告仅证明其当时的版本。

发现设计缺口时先写问题、影响、建议和待决事项；涉及设计/契约/成本变更必须由用户确认后更新 SSOT。审查方不能以“更安全/更合理”为由静默改成不同产品。

本次已经识别但尚未代用户裁决的例子：路径身份冲突返回 403 还是按头解析、八维部分更新策略、库存时效边界、房间 ω 的传递与冻结、stats 文字 12 项而表列 13 项、allergen_tags 保存位置、全局过滤的适用范围。分别在对应步骤开工前解决；不要求为远期未知细节一次冻结全部实现。

## 3. 阶段状态机

```text
LOCKED --前一步由 Codex PASS--> READY
READY --开发方声明本步范围--> IN_PROGRESS
IN_PROGRESS --提交验收包并停手--> REVIEW_PENDING
REVIEW_PENDING --Codex 独立审查--> PASS / CHANGES_REQUIRED / BLOCKED
CHANGES_REQUIRED --本步整改--> IN_PROGRESS
BLOCKED --外部条件或明确决策齐备--> IN_PROGRESS
PASS --受审版本/依赖变化使证据失效--> REOPENED
REOPENED --补验收提交--> REVIEW_PENDING
```

- 已完成 PC01–S06 的状态保留为历史审查记录。剩余工作按合并计划分组，当前 G1=READY；G2–G5 按组序连续施工，不以每个子步骤的 LOCKED 状态阻止用户已授权的大组。开放施工不等于 Codex 已签发验收 PASS。
- FAIL 对应台账 `CHANGES_REQUIRED`；BLOCKED 代表必须证据、外部服务、设备或决策缺失，不能当成通过。
- DEFERRED 只用于用户明确允许延期的专项，不表示完成；Room 交互已纳入 G1，统一审查前仍未获正式 PASS。
- 一个步骤在 REVIEW_PENDING 时不得继续改受审代码；若必须修，提交新版本并作废被替换的证据。审查与开发双方先协调同一基线，避免读到一半改动。
- 同一时间按顺序施工一个开放大组。同一大组内步骤按 `docs/review/CONSOLIDATED_REMAINDER_PLAN.md` 的依赖连续开发，组末封存证据后可进入下一组；不得在最终统一审查前把任何子步骤自签为 PASS。已有 Codex PASS 仍只覆盖原受审版本，后续共享代码变更须在统一审查中重验受影响范围。
- PASS 只覆盖指定步骤、文件/依赖和数据版本；不能授权全部后续步骤。已 PASS 步骤被重改，Codex 判定影响范围；受影响步骤重开、后继暂停，未受影响结果无需无理由重跑。

在合并工作流下，单步 `LOCKED` 表示该子项尚无独立审查结论，不再单独阻止已授权大组按计划施工；正式结论仍待五组全部完成后的统一复审。外部条件或组内依赖未满足时，相关工作仍须标记 BLOCKED。

## 4. 每步提交前的开工卡

开发方开始每个大组先提供以下开工卡，并核对组内依赖及既有 PASS 记录；不要求组内每个子步骤分别等待 Codex 放行：

```markdown
步骤：Sxx / 名称
前置放行：上一审查记录编号、受审版本
目标：本步必须实现/核验的行为
允许文件：具体路径；若新建先说明职责
接口与依赖：请求/响应、调用方、共享口径
异常与边界：可执行的正例、反例、时序/并发情形
测试与隔离：运行命令、测试库/会话、外部服务方式
设计缺口：无；或已确认决策的链接/记录
后端报备：改什么、为什么（涉及后端必填）
```

本次用户已授权制定计划，不自动授权购买服务、无限量 LLM 调用或使用未确认的素材来源。按步骤解决必要条件，不创建额外的日常许可流程。

## 5. 验收包必须包含什么

每轮目录：`docs/review/stages/<步骤编号>/rNN/`，例如 `PC01/r01`、`S01/r01`；模板中的 Sxx 泛指当次实际步骤编号。重审递增目录，保留旧结论，不覆盖历史失败记录。

| 文件/目录 | 必须内容 | 责任方 |
| --- | --- | --- |
| `SUBMISSION.md` | 任务/验收条目逐项自测结果、变更路径、接口/迁移变化、已知限制 | 开发方 |
| `BASELINE.md` | 日期时区、HEAD 或无提交状态、工作树差异摘要、环境版本、源码清单和数据集身份 | 开发方提供，Codex 复核 |
| `SOURCE_MANIFEST.json` | 受审代码、配置、锁文件、相关素材/测试的路径与 SHA-256；含相关未跟踪文件 | 开发方提供，Codex 复核 |
| `CHECKS.md` | 命令、cwd、开始/结束时间、退出码、日志路径；没有执行写未执行 | 开发方 |
| `logs/` | 测试、构建、启动、服务端必要输出，不能只有截断的成功尾行 | 开发方 |
| `browser/` | 真实操作顺序、URL/视口、身份、截图/录屏、console/network、失败与恢复 | 涉及 UI 时开发方提供，Codex 独立复测 |
| `data/` | 隔离库验证摘要、输入/输出摘要与哈希、独立计算结果；不提交凭据/真实私有数据 | 涉及数据时提供 |
| `REVIEW.md` | 逐条结论、问题级别、证据、范围限制、最终判定与后继许可 | 仅 Codex 签发 |

不适用项写明原因，由 Codex 判断是否确实不适用；不能删掉失败日志、跳过必测流程后说“无需”。源码变化后必须重新生成清单，不能继续引用旧绿灯。

对没有 Git 提交的工作区，源码清单 + staged/unstaged diff + untracked 清单也可固定版本；不要求为满足模板而擅自 `git add .`、提交或重置。不要把原始密钥、令牌或整个用户数据库放进日志/包内。

## 6. Codex 每轮审查顺序

1. **入场核对**：确认当前步骤已开放、前置 PASS 有效、受审版本可定位、开发方已停止修改；缺失则 BLOCKED。
2. **设计审查**：对照 SSOT 与本步标准，检查命名、数据/算法契约、视觉和批次边界；未批准偏离先 FAIL，不用“实现很多”抵扣。
3. **代码审查**：读 diff 及调用链，关注输入→唯一实现→写入→消费→返回→展示；搜索所有入口，不只看被点名的一处。
4. **自动化复验**：Codex 实际运行对应测试/构建，核对退出码与完整输出；开发方日志只作线索。不能运行则 BLOCKED，明确具体缺少什么。
5. **真实交互/数据复验**：涉及 UI 实际点击/拖拽；涉及算法独立手算/固定样本；涉及数据库检查前后状态；涉及多人使用独立身份和连接。
6. **直接依赖回归**：检查相邻页面、共享数据和前后端链路；不能改单一 driver 就只看它自己。
7. **出具结论**：将实际观察、未验证范围和必须整改项写入 REVIEW，更新台账，明确是否允许下一步。

如果审查中发现范围外的严重问题，记录新编号并判断依赖。影响当前正确性/数据安全的先阻断；不相关的后续能力留到对应已规划步骤，不能借审查无边界重构。

## 7. 通用验收矩阵

| 维度 | 必须达到的标准 | 直接拒绝的情况 |
| --- | --- | --- |
| 设计契约 | 字段、枚举、路由、算法和批次匹配有效 SSOT | 偷换算法/框架/路由、用旧归档覆盖现行设计 |
| 功能 | 正常、空态、失败、恢复与重复操作可完成 | 假按钮、假成功、占位冒充完成 |
| 身份与数据 | 写入口/消费端全覆盖，越权拒绝或按批准规则解析 | 只修 body 漏 path、角色串数据、非法请求脏写 |
| 输入边界 | 八键完整、有限值/范围正确，字段边界与 UI 一致 | clamp 掩盖持久化坏数据、部分向量覆盖丢键 |
| 时间/并发 | 唯一截止/时钟口径、幂等、阶段约束、恢复一致 | 离线停表、结算后改票、重复结算 |
| 算法与实验 | 独立期望值、硬约束、真实样本和公平对照 | 测试抄生产期望、全否决仍赢家、预置曲线 |
| 数据真实性 | 来源、版本、数量拆分、清洗/拒绝可追溯 | 合成当真实、异构总数当菜品数、重复行凑规模 |
| 视觉与性能 | 单色令牌/玻璃分级，布局可点，查询不随候选产生 N+1 | 按钮被遮却只测 scrollHeight、整页全开折射 |
| 证据质量 | 代码/数据版本绑定，图像稳定，日志可复验 | 旧截图当新结果、截图只拍转场背景、无日志声称通过 |
| 交付文档 | 运行步骤与实际一致，限制明说，账本与台账同步 | 自测结果写成 Codex 放行、隐藏未测范围 |

## 8. 严重程度与放行阈值

| 等级 | 定义/例子 | 门禁处理 |
| --- | --- | --- |
| P0 | 凭据泄露、任意代码执行、破坏性数据损坏等紧急问题 | 停止受影响开发和测试写入，先处置；不可放行 |
| P1 | 核心路径无法进入、全否决仍选中、状态机卡死、不可恢复/重复结算 | 本步 FAIL，修复并独立复验 |
| P2 | 明确契约偏离、漏入口校验、过期库存计入、必需交互/素材缺失 | 影响本步或其前置时 FAIL；本步关闭前必须修完 |
| P3 | 不影响本步正确性/必需体验的低风险文案或维护建议 | 可登记为非阻断，注明理由和处理步骤 |

**PASS 的必要条件**：本步每个必需条目通过；影响本步/前置的 P0/P1/P2 为 0；独立测试和必要真实交互已执行；证据齐全；受审版本一致；没有把外部条件缺失当成功。

没有“基本通过”“先做下一步再补”“条件通过”这种放行状态。历史 warnings 不一律判失败，但要列内容、影响和判断依据；新增未解释的运行时异常、未处理 promise rejection、关键请求失败不能放过。受控的离线/非法输入测试应记录预期错误及 UI 提示，不能与意外错误混在一起计数。

当前必需功能若要延期/降级，必须由用户明确改变范围并同步 SSOT 与计划；这叫范围变更，不是审查方豁免。

## 9. 自动化检查与独立证据

### 9.1 现有命令

从仓库根目录的 PowerShell 执行；每条保留其 cwd、输出与退出码：

```powershell
# 后端（独立命令，不因后面的成功覆盖前面的退出码）
Push-Location D:\EatWhat\backend
python -m pytest -q
$backendExit = $LASTEXITCODE
Pop-Location

# 前端
Push-Location D:\EatWhat\frontend
npm run build
$frontendExit = $LASTEXITCODE
Pop-Location

# 需前后端运行、可用浏览器/CDP，先确认脚本连接的是隔离测试环境
node scripts/home-fit.mjs
node scripts/refill-fresh.mjs
node scripts/sandbox-sync.mjs
```

这些命令是开发侧现有复验入口；执行者须遵守其工具环境的浏览器操作规则。受限于工具能力时，可由审查方在真实浏览器复验相同断言并留证，不能绕过环境限制或伪造脚本成功。项目脚本本身若作为交付门禁，也必须检查可运行、失败能非零退出；过时脚本不应无限期豁免。

### 9.2 按变更选择必跑项

- 后端变更：本步针对测试 + 后端全量；影响 API 的前端流程实际回归。
- 前端变更：build + 涉及页面真实操作；Home/store/router/沙盒/划卡变更加三条界面门禁及底部导航。
- schema/迁移/数据工程变更：隔离库的新库建立、旧样本升级、失败行为、幂等；不在真实演示库试错。
- 多人变更：两个独立身份全流程、截止、全断线、恢复、完成后拒投；S07/S19 增加四身份和真机扫码。
- 大屏/统计变更：固定小样手算、实际大数据、组合过滤、空态、下钻和真实导出。
- 纯文档变更：链接/路径、章节引用、步骤依赖、状态一致性和 SSOT 覆盖检查；不为文档改动声称运行过业务测试。

测试条数不是门槛；87/106/123 等历史数字不能硬编码成“至少这么多就过”。新增用例不允许删旧断言、扩大容差、skip 严重问题来换绿色。

## 10. 真实浏览器与隔离数据的专项规则

用户明确要求审查覆盖代码、独立测试与真实运行。对 PC01 必须实际运行仿真、独立复算、换种子或参数复跑，核对隔离库与输出；对 PC02 必须真实推荐请求捕获 SQL 次数、复测耗时与结果一致性；对 PC03 必须实际扫描并用可移除的违规样例证明非零退出，同时真实点击移动页检查样式回归。页面已存在的部分均用真实浏览器核验，不能以 API 调用替代点击。尚不存在的大屏显示验收明示留到 S17，不能宣称当前已测，更不能提前铺后台来完成准入。

1. 以真实用户入口点击/拖拽完成任务；直接打开 URL、调 API、改 DOM 或截图不能单独证明导航、划卡或扫码可用。API/DOM 检查是补充证据。
2. 等待目标页面真实内容和转场结束；记录 URL/标题/关键内容，截图后实际查看图像。AutoAnimate 离场节点、数字滚动中的瞬时值要等稳定再比较，不能过早误报。
3. 首页 390×667、390×844 都测 scrollHeight/scrollWidth、元素矩形、可见边界、按钮命中和真实点击。不得通过裁切隐藏内容骗过“不滚动”。
4. 两端测试先验证独立身份；模拟网络中断要保留服务端结算与恢复证据。桌面正常不等于真机正常，H5 打开不等于 APK 安装成功。
5. 数据库写入测试在新建临时库或明确命名测试副本进行；在应用导入/启动前确认数据库 URL、dependency override、后台任务和 WS 使用的 session 全部隔离。
6. 若构建审查用 FastAPI app，用正常 `include_router` 挂载并验证实际依赖覆盖；禁止直接复用 APIRoute 列表后假定已隔离。先做哨兵验证，未证明隔离前不得执行写探针。
7. 记录真实演示库只读摘要/哈希；SQLite 有 WAL 或应用并发写入时要记录条件，不用单个主文件哈希宣称逻辑状态没变。不得复制/恢复/删除用户数据来掩盖测试污染。
8. 页面与日志脱敏；只关闭自己创建的测试标签页，临时视口用完恢复，不关闭用户页面。

## 11. 通过、退回与阻塞的审查记录模板

```markdown
# Sxx / rNN 审查
审查时间：YYYY-MM-DD HH:mm（Asia/Shanghai）
审查方：Codex
```

## 13. 文档与变更管理

- 开发方在提交说明中补充事实与自测结果；账本可以写“已实现、待 Codex 复核”，不得写成独立验收通过。
- Codex 写 REVIEW 并更新台账的放行/撤销记录。人工可以复制 Codex 已给出的结论，但必须附原审查记录，不能改变结论或扩大范围。
- 原报告不覆盖；新证据指向新目录。计划改变时写明原因、影响的步骤、是否涉及用户设计决策；不能只改表格顺序绕过未通过的一步。
- 严重回归重开原步骤或创建其修复轮次，先修再验；不把问题藏到 S20“最后统一处理”。

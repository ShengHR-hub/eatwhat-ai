## 1. 配色总纲

- 黑、灰、银、白单色系，走克制的高级感路线。
- 原暖橙 + 鼠尾草绿 + 奶油白方案**作废**，不再引用。
- 分工原则：黑与银负责气质（首页、揭晓、导航），白/浅灰负责可读（内容页实底），银渐变只做点缀、不做信息载体。

## 2. 三个背景的分工（全部来自 Vue Bits，原生 Vue，单文件可直粘）

| 背景 | 用在哪 | 关键设置 | 禁忌 |
|---|---|---|---|
| **Grainient（谷物）** | 移动端**全局底**，所有页面打底 | 三色全换银灰：深色版 `#3a3a40 / #17171a / #55555e`；timeSpeed ≈ 0.2（接近静止）；颗粒保持细腻、低强度 | 不许用默认蓝紫配色；速度不许快；颗粒不许粗 |
| **Liquid Chrome（液态铬）** | **仅**首页顶部区域 + 共识揭晓页 | 底色保持近黑 `#1a1a1a`（最亮不超过 `#222226`，靠深底衬银）；可关交互跟随以省性能 | 不铺整页、不进内容页；文字不直接压在铬面上（必须落在玻璃或实底上） |
| **Silk（丝绸）** | **仅**启动页 / 登录页（只看几秒的页面） | 银灰色；Speed 从默认 5 降到 1–2 | 不做全局底——其一明暗条纹太抢内容，其二墨池已用 Silk 做全局背景，两个作品不能撞脸 |

补充规则：
- 内容密集页（列表、详情、表单）允许把 Grainient 冻结为静态帧或大幅降帧，底只是氛围，不许和内容抢注意力、抢性能。
- 深色底压食物图片有压食欲的风险，因此菜品图片一律放在实底卡片里展示，不直接贴在动效底上。

## 3. 三层架构：「底再动，组件不受影响」的保证

- **第 0 层 · 底**：§2 的背景，只负责氛围，不承载信息。
- **第 1 层 · 玻璃组件**：悬浮小件用 Apple 液态玻璃材质（§4）。半透明透底，但透出的是经 backdrop 模糊磨砂后的底，文字压在雾面上读，与底的流动解耦。
- **第 2 层 · 实底内容**：菜品卡片、列表、表单一律实底（白或深灰实色），完全不透底。

硬性规则：
1. 底必须低对比、慢速（见 §2 参数），从源头上不干扰。
2. 玻璃只给小面积悬浮件（WeatherPill、顶部导航条、底部 Tab 栏、模式切换器、抽屉把手）；玻璃面积小也是性能要求——backdrop 模糊叠在动态 WebGL 底上吃手机 GPU。
3. 正文与数据一律进实底组件，任何情况下不直接写在动效底上。
4. `backdrop-filter` 不被支持时，玻璃组件降级为实底填充 `rgba(246,246,246,0.85)`，功能不受影响。

## 4. 玻璃组件材质（WeatherPill 为样本）

来源：Apple 官方 Figma「macOS 27」Materials 页，2026-10-23 实测提取；副本「macOS 27 (Community)」在用户 Figma Drafts 内。完整参数表（两层填充/7 个阴影/Glass 折射参数）见 `WEATHERPILL_GLASS.md`，此处只留开发直接用的结论：

- 样本：**Liquid Glass - Small（Light 变体）**，48×48 全圆角（CSS 999px），专为小面积悬浮元素设计。
- 核心数值：填充 4 层半透明叠色（`#F8F8F8·20% / #444444·60% / #FFFFFF·25% / #000000·25%`）；内阴影 3 个 + 外阴影 4 个塑形；Glass 参数 Refraction 70 / Depth 30 / Dispersion 20 / Frost 6 / Splay 20（CSS 无等价属性，仅作设计参照）。
- Web 生产版 = 经典材质实测值做透底（`#F6F6F6` 半透明 + 背景模糊 60）+ 上述阴影塑形，数值全部来自原文件：

```css
.weather-pill {
  border-radius: 999px;
  background: rgba(246, 246, 246, 0.48); /* Thin 档；Ultrathin 0.36 / Medium 0.60 */
  backdrop-filter: blur(60px);
  -webkit-backdrop-filter: blur(60px);
  box-shadow:
    inset 0 40px 10px -40px rgba(40, 40, 40, 1),
    inset 0 -40px 10px -40px rgba(40, 40, 40, 1),
    inset 0 40px 30px -40px rgba(230, 230, 230, 1),
    1.25px 0 0 -0.75px rgba(208, 208, 208, 1),
    -1.25px 0 0 -0.75px rgba(208, 208, 208, 1),
    0 0 0 0.5px rgba(232, 232, 232, 1),
    0 8px 15px rgba(0, 0, 0, 0.02);
}
```

- Figma 未给 saturate 值；开发中如自行添加，须在注释中注明为自选参数、非 Apple 原值。
- Dark 变体数值本次未提取；若后续玻璃组件要上深色玻璃，再进副本补取。

## 5. 答辩展示（2026-10-23 用户拍板）

### 5.1 问题

食刻是移动端产品，答辩投屏时先天吃亏：
- 投影幕是 16:9 横屏，手机竖屏投上去只占中间一条，画面小、字更小；
- 触控操作评委看不见手指，划卡这类核心手势的演示效果打折；
- 投屏链路（无线/线材/网络）本身是现场风险点。

### 5.2 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 真机投屏 | 手机经 scrcpy/投屏软件上大屏，现场手持操作 | 最真实 | 竖屏窄条问题无解；手势不可见；链路风险最高 |
| B 浏览器手机框演示 | 移动端前端跑在 PC 浏览器里，以手机尺寸居中 + 设备边框展示，鼠标操作 | 画面可控、字看得清；划卡拖拽鼠标可模拟（GSAP Draggable 支持鼠标） | 没有真机触感；仍是竖屏构图 |
| C **展示模式（大屏只读端）** | 新增一个全屏展示页：输入房间码后订阅房间实时状态，大屏展示成员、划卡进度、共识揭晓（Liquid Chrome 全屏）；评委扫码用自己手机进房一起划卡 | 把「多人实时决策」这个核心卖点变成现场互动，展示效果最强；横屏全屏利用投影；技术上只多一个只读页——WebSocket 在 v2.2 已锁定为只订阅、不写成员，展示页零新增业务逻辑 | 需多开发一个展示页（小工作量，建议独立小批次，排在揭晓页之后） |
| D 录屏兜底 | 提前录好完整流程录屏 | 零现场风险 | 无互动、说服力弱；只能兜底，不能当主方案 |

### 5.3 拍板方案：网页展示版（聚合）+ 移动端真机视频

用户决定（2026-10-23）：不采用 C 的互动展示模式，改走「**全部功能完成之后，再做一个网页展示版**」——

- **移动端按原计划做**（本规格 §1–§4 不变），**PC 管理后台按原计划做**，两者开发期间互不为展示让路。
- 全部功能冻结后，新增收尾批次做 **网页展示版**：把移动端的全部功能与后台网页端的全部功能归总进一个网页端，答辩时以展示版为主进行投屏演示。
- **移动端效果的交代方式**：提前录一份移动端真机使用视频，答辩时播放展示；若老师问起移动端效果，口径为「移动端竖屏投屏展示效果不佳，故将全部功能归总到网页端一并展示，移动端另有真机录屏」。
- 桌面端定位随之定案：桌面端 = **管理后台 + 网页展示版**，不做独立的桌面用户端产品。

### 5.4 展示版实施护栏（防止「直接 copy」低估工作量）

1. **同代码库、同一套组件**：展示版与移动端共用 Vue 工程与组件，只新增桌面壳（顶部/侧边导航 + 内容区）；严禁另起工程复制一份代码，后续改一处要同步两处必出事故。
2. **移植策略分级**：多数移动页面在展示版内容区内**限宽居中**原样呈现（布局不重做）；仅首页、共识揭晓、实验大屏三处做横屏扩展利用大屏宽度。不许把每个页面都重排成桌面布局，工作量会失控。
3. **时机锁定**：展示版必须在功能冻结后一次性移植（对应 MASTER_SPEC 批次 5），开发中期不提前做、不双线维护。
4. **论文如实表述**：展示版在论文中表述为「答辩演示聚合端」，系统形态仍为移动端 Web + PC 管理后台，不虚构第三个产品端。
5. **现场兜底**：真机（装好 APK）+ 投屏线随身带，老师若坚持看真机实机，可当场切真机演示；展示版与视频都出问题时以真机为准。
